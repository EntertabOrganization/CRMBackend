# Logical Files and immutable Versions

Managed SPA transfer objects have immutable `file_artifact_bindings` provenance. The installed owning-domain content authority runs before grant issuance and before/after byte I/O, using current membership, entitlement, job access and exported field/filter/Item scope. Expired exports and revoked authority invalidate cached grants; copied File/Version metadata does not remove the original object policy. Private reports/exports cannot use public File or folder delivery, editor sessions or document-template repurposing. Deploy the additive artifact-authority migration before enabling these paths. Standalone Files composition fails closed for artifact objects until an authority is installed.

Files own mutable names, locations, lifecycle status and the current Version pointer. Versions own immutable object identity, checksum, size, MIME type, creator and creation time. Normal File and Version API responses never expose objectKey. Scan status changes are constrained separately; blocked content cannot be relabelled clean.

File authority combines a platform action with the current storage/folder chain and direct FILE assignments. Every File remains inside its original Workspace and storage. Direct ACL overrides replace inherited authority. Mutations require EDIT (or the operation's stronger authority) and an optimistic resource version. Copy requires readable clean content and ADD at the destination; copied Files inherit destination ACLs and do not duplicate capabilities or business bindings.

Version restoration creates a new Version number and current pointer. It never edits the selected old Version. Clean history can recover a blocked current File; blocked or unprocessed historical content cannot be restored. Trash preserves the original folder, prior status and retention deadline. Restore rechecks the destination, name conflict and current scan result; quota does not prevent recovery of an existing trashed File.

Quota includes referenced bytes across all retained Versions, including trash and history, plus unexpired upload reservations that have not yet produced a Version. Platform defaults are 100 MiB per new Version and 5 GiB per Workspace. Effective limits are the minimum of these defaults, Workspace settings (`fileMaxBytes`, `fileStorageQuotaBytes`) and live grants (`files.max_file_bytes`, `files.storage_bytes`). Disabled grants prohibit growth. Copy and Version restoration reserve logical Version growth even when immutable objects are shared. Safe reads, trash and File recovery do not add bytes. The Workspace revision fence covers quota policy and competing growth; PostgreSQL independently enforces final-state limits for new Versions and upload reservations.

PostgreSQL also guards same-Workspace/storage parent paths, normalized active sibling names, current-pointer metadata/scan consistency, immutable Version identity and content metadata, creator tenancy, retention/legal holds on deletion and object namespace. Aliases of one immutable object must agree on checksum, size, MIME type and scan status. A scanner changing a shared object's verdict must update every alias and every affected current File status in the same transaction. Merely quarantining one alias cannot leave another active alias exposed.

Folder copy stages all readable clean File/Version copies before writing the graph, so a denied File or quota failure cannot leave an empty or partial copied tree. Folder trash checks descendant File authority and advances File share versions; restoring a folder does not revive independently trashed Files or older public capabilities.

Upload sessions persist creator-scoped idempotency keys, declared checksums and quota reservations for 24 hours. Parts accept canonical base64 up to 4 MiB each, with at most 100 immutable numbered parts. Retrying a part requires the same checksum and size. Upload JSON is bounded while streaming: 6 MiB for parts, 64 KiB for session metadata and Version-session creation, regardless of the declared Content-Length. Authentication runs before body handling. Responses omit private object keys. Version-only creators require File EDIT authority and the version-create action without requiring folder ADD authority.

Private local objects live under `FILE_OBJECT_ROOT` (default `.local-file-objects`), outside public assets; deployments with multiple workers must provide the same durable volume. The volume must support hard links: a private temporary file is written and synced before an atomic link publishes its immutable key. Competing writers cannot expose partial bytes or replace content. Completion verifies every part and the complete SHA-256 checksum. CLEAN content stays PROCESSING until processing completes; immutable `processedAt` proof also prevents restoring unprocessed history into ACTIVE. Completion retries reuse the same File and Version and return the durable receipt while processing is pending. Missing processor configuration rejects completion with FILE_PROCESSOR_UNAVAILABLE before creating a File; a configured provider outage retains verified bytes and a PENDING Version for automatic retry.

Configure `FILE_PROCESSOR_URL` and `FILE_PROCESSOR_TOKEN` for a trusted malware scanner and preview/text processing service. HTTPS is required except for loopback development endpoints. The adapter POSTs immutable bytes with their MIME Content-Type, a Bearer token, `x-content-sha256`, and a content/MIME idempotency key. The service must authenticate requests, independently verify the checksum, perform scanning and required processing, and return JSON `{ "checksum": "<verified SHA-256>", "scanStatus": "CLEAN" | "BLOCKED", "processed": true | false }`. Only report processed=true after the processing pipeline finishes; asynchronous work reports false. Verdicts must match the exact input checksum. Redirects are never followed; responses are limited to 4 KiB and requests time out after 15 seconds. Provider diagnostics and credentials are never copied into API responses or audit.

Schedule `POST /api/v1/internal/crm/jobs/upload-processing` with the same internal job token and bounded limit used by cleanup. Claims commit before provider I/O, verify sealed bytes again, retry failures with capped backoff, reclaim expired leases and fence stale verdicts. Processing runs independently of uploader membership, original folder location, read-only flags, session expiry and reduced quota because it updates existing immutable content rather than accepting growth. Shared aliases and current File statuses commit with scan/processing proof in one transaction; blocked content cannot be relabelled clean. Historical processing does not change a newer current Version, and trashed content stays trashed. The worker records audit/outbox evidence. Scheduler sent counts mean a valid provider verdict was committed, which may still report asynchronous processing pending.

Abort commits terminal session state and releases the reservation without deleting bytes inside the request transaction. The authenticated scheduler endpoint `POST /api/v1/internal/crm/jobs/upload-cleanup` accepts `limit` (1–100, default 25) and requires `x-internal-job-token` matching `INTERNAL_JOB_TOKEN`. Run it regularly. It also expires unaccepted sessions, commits leased claims before storage I/O, removes the entire closed multipart namespace (including unrecorded temporary objects), and records cleanup audit/outbox evidence. Failures retain durable retry state with capped exponential backoff; expired leases can be reclaimed and stale finishes cannot commit. Missing objects are successful retries. Closed namespaces are swept again daily to collect bytes from late, pre-abort writers. Staging identities cannot be referenced by File Versions, and accepted File bytes are excluded. Cleanup remains system work after a creator loses membership.

Once verified bytes are sealed into a Version, multipart staging is closed even while processing is pending. Cleanup removes only its staging namespace; accepted immutable objects are retained for processing and File delivery. Repeated completion remains available after staging cleanup. Configure and operate the external scanner/processing service and both scheduler jobs in production; HTTP fixtures verify adapter behavior but do not certify an external malware engine.

Permanent purge requires FULL authority, a current resource version and trashed content. File, Version, storage and ancestor retention deadlines and legal holds block the entire transaction. Folder purge preflights the complete bounded subtree, then removes its Files, Versions, ACLs and folder capabilities together with audit/outbox evidence. Accepted upload receipts remain irreversible tombstones, so stale completion and idempotency retries cannot recreate purged content. Accepted content moved outside the subtree retains its processing session even after the original upload folder is removed.

Schedule `POST /api/v1/internal/crm/jobs/file-object-garbage` with `x-internal-job-token` and `limit` (1–100, default 25). Purge queues durable cleanup intents in the metadata transaction; physical deletion happens only after commit. Shared objects remain until their final Version reference is removed. PostgreSQL retires those identities permanently and rejects new references, including independent SQL writes. The cleanup worker commits leases before storage I/O, retries provider failures, fences stale finishes and treats missing bytes as successful deletion. Retired namespaces are swept daily to remove late writes. Cleanup proofs and upload tombstones must be retained. Deploy all three scheduler jobs with access to the shared durable object volume.

Authenticated `GET /api/v1/files/:id/download` requires `file.download`, current File ACLs and readable owning Task results/templates and Calendar Events. Configure a shared `FILE_DELIVERY_SECRET` of at least 32 bytes on every API process. The response contains a two-minute signed `deliveryPath` with an opaque nonce; it contains no object key. The durable grant stores only the nonce hash, actor and exact current Version/share revision. Fetching that path rechecks membership, action, ACLs, owning-record authority, lifecycle and CLEAN/processed proof. Version changes and trash/restore invalidate old paths. Secret rotation also invalidates outstanding signatures.

The relay verifies byte size and SHA-256 before committing single-use consumption and FILE_DOWNLOADED audit/outbox evidence. Failed content reads remain retryable. Concurrent source/grant changes reject the transaction before bytes leave the server. Consumption proofs are immutable and retained, including after File purge. Delivery uses a bounded whole-file buffer (the platform upload maximum is 100 MiB); byte ranges are not exposed. Responses force attachment/octet-stream, encode filenames safely and return no-store/no-referrer/nosniff/sandbox headers. The signed path is a bearer capability within its lifetime and must be kept private. The existing process-local public limiter applies to the relay; ingress can provide a shared fleet limit.

Public File/folder capabilities support signed byte delivery with live policy, issuer, scan, existing private Task/Calendar binding checks and atomic download limits; see `PUBLIC_LINKS.md`. Generic attachments and the default FilePort now use live File and owning-record authority; see ATTACHMENTS.md. No full Files module completion is claimed.
