# Storage and folder read foundation

Files owns one canonical Project storage and root folder, provisioned lazily through the existing Project resource port. Reads require `storage.read`/`folder.read`, active internal Workspace membership, and a live Project-derived or independently granted access source. Project membership synchronization changes only its own source. Archive makes the storage read-only; unarchive restores it. Hard deletion detaches and freezes the storage while preserving its root and retained access/history.

`GET /file-storages`, `GET /file-storages/:id`, `GET /file-storages/:id/root` and `GET /folders/:id` support Personal, Company, Project and System storage. Personal owners default to FULL; Company members default to READ and Workspace owners to FULL; System content requires a retained access source or ACL grant. Inactive storage is invisible. Every read requires its action permission and live Workspace membership; broad RBAC alone never grants Personal or Project access.

Folder reads walk the complete same-Workspace/storage parent chain, reject cycles, missing parents and trashed ancestors, and apply storage-to-child inheritance/overrides. An override replaces inherited grants, including Project defaults; absent matching subjects grant no access at that override. Explicit child sharing can authorize a folder without exposing its storage or parent metadata. USER, ROLE, DEPARTMENT, DEPARTMENT_TREE, PROJECT_ROLE and WORKSPACE grants reevaluate live subjects. External guest assignments do not grant ordinary Workspace API access.

`POST /file-storages` creates Personal/Company/System containers and one root atomically. Personal and Company canonical duplicates are rejected. Project creation delegates to the owning Project tool port and returns its existing canonical resource on retry. `POST /folders` requires an active parent in the requested storage, ADD or greater effective access, `folder.create`, and writable storage. Active sibling names are case-insensitive, trimmed and NFC-normalized.

Composite keys and deferred checks enforce tenant/storage parent relationships, acyclic hierarchy, one active root per storage and canonical containers. Storage-row locks serialize folder graph changes. Historical Prisma model names `ProjectFileStorage` and `ProjectRootFolder` remain for compatibility; they now represent all storage types and folder depths.

Folder move/copy/trash/restore and storage/folder/File ACL configuration are implemented. Logical Files, immutable Versions and multipart upload sessions include authenticated scanner/processing integration, durable processing retries, and staging cleanup. File/folder permanent purge commits retention-checked metadata removal and durable last-reference cleanup intents atomically, with physical deletion handled by a leased worker. See [FILES.md](FILES.md) for upload and worker deployment configuration, [DOCUMENTS.md](DOCUMENTS.md) for document templates and generation, [ACL.md](ACL.md) for assignment behavior, and [PUBLIC_LINKS.md](PUBLIC_LINKS.md) for File/folder capabilities and public metadata.

Private and public signed download paths and single-use byte delivery recheck File and existing owning-record authority. They require a shared signing secret; see `FILES.md`. Public File/folder metadata, capability management, tree-scoped delivery and atomic download accounting are integrated; see `PUBLIC_LINKS.md`. Existing private Task/Calendar bindings deny anonymous File sharing. Generic attachments must integrate with these gates when implemented; the existing File attachment port remains unconfigured until generic attachment access checks are implemented. The authoritative remaining operation inventory is the repository-root IMPLEMENTATION_PROGRESS.md; no full Files module completion is claimed.
