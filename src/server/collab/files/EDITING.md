# Document editing

The lock foundation is implemented. POST /api/v1/files/:id/locks acquires a 15?900 second lease (300 seconds by default), returning its random lockToken once. Only a hash is persisted. EDIT requires file.lock and EDIT File ACL; SYSTEM_PROCESS and WORKFLOW reservations require FULL File ACL. DELETE /api/v1/files/:id/locks/:lockId verifies current action/ACL/context, lease ownership and lockToken. POST /api/v1/files/:id/locks/:lockId/force-release requires file.force_unlock, FULL File ACL, the lease version and a reason; FILE.FORCE_UNLOCKED audit evidence is recorded.

Existing active leases block competing acquisition, File metadata/content/lifecycle mutation, Version upload creation/completion and folder trash containing leased content. Authorized immutable reads/copies remain available. Expired leases are retired before replacement, retain distinct identity and cannot be revived with old tokens. Released lease evidence cannot be deleted/reset. PostgreSQL independently rejects overlapping lease ranges and File mutation under an active lease. Responses carrying freshly issued lock tokens prohibit caching. Release/force-release remains possible for authorized cleanup when content is quarantined or trashed.

Forward migration 20261011190000_document_edit_leases adds lease and edit-session storage, immutable history, tenant/provenance guards, exclusivity, expiry bounds and Workspace revision fencing. file.edit, file.lock and file.force_unlock are included in the existing permission catalog and seed. Existing File/Folder/Upload mutation guards now honor exclusive leases. FILE_LOCK_ACQUIRED/FILE_LOCK_RELEASED use the transactional outbox.

EnvironmentEditingProvider provides local UTF-8 text editing primitives (plain text, Markdown and HTML) and an authenticated editor-broker adapter for vendor providers. FILE_EDITOR_URL is a trusted HTTPS broker base URL (loopback HTTP is allowed for fixtures); FILE_EDITOR_TOKEN is its server credential. The broker implements POST <base>/sessions/open, /save and /close. Requests/responses bind id, workspaceId, fileId, userId, baseVersionId and provider; open must use the supplied id as providerSessionId and return a HTTPS editorUrl. Save accepts an immutable saveId and returns the same identity/saveId, MIME, canonical dataBase64 and SHA-256 checksum. Requests use stable operation idempotency keys, bounded response bodies and timeouts. Caller-supplied vendor bytes never substitute for a provider save receipt. Provider failures and mismatched identities/checksums fail closed without reflecting credentials. These primitives have only exercised a deterministic local broker fixture, not Google/Microsoft/OnlyOffice services.

POST /api/v1/files/:id/edit-sessions accepts provider (INTERNAL_DOCS by default), mode (EXCLUSIVE_LOCK by default), and leaseSeconds. A reservation and optional exclusive lease commit before provider I/O. Activation rechecks current File.edit authority, EDIT ACL, owning-record access, clean content, source Version and live lease. The launch response includes editorUrl for a vendor editor or dataBase64 for local text, and the fresh exclusive lockToken. These values are excluded from ordinary session/File projections. Provider failures compensate the reservation and schedule durable cleanup.

GET /api/v1/files/:id/edit-sessions lists the caller's sessions with bounded page/limit pagination, status/provider/mode filters and startedAt/lastActivityAt sorting. GET /api/v1/edit-sessions/:id rechecks current authority and returns safe metadata. Heartbeat accepts version, lockToken for exclusive sessions, and leaseSeconds; it cannot revive released or expired ownership. Abort accepts version and an exclusive lockToken and retains the original immutable Version. Forced lease release also aborts the associated session and queues cleanup.

POST /api/v1/edit-sessions/:id/complete accepts version and an exclusive lockToken, plus dataBase64 for INTERNAL_DOCS or saveId for a vendor broker. A hash binds the first save request; equal retries reuse its immutable receipt, and changed saves conflict. Each provider/storage checkpoint reauthenticates and rechecks the source and lease. The upload receipt commits before multipart/object writes. Editor uploads are hidden from ordinary upload routes. Completion publishes exactly one immutable Version through the normal quota, malware scan and processing pipeline, completes the session and releases its lease in one transaction. Scanner outages retain one accepted PENDING Version for the existing processing worker. Concurrent collaborative edits of a stale source cannot overwrite the winner.

Migration 20261011200000_document_edit_pipeline adds immutable save/upload provenance and provider-cleanup leases. POST /api/v1/internal/crm/jobs/document-edit-cleanup uses the configured scheduler token and bounded limit (1-100); run it regularly alongside upload-cleanup, upload-processing and file-object-garbage. It expires stale sessions and retries provider closure after committing a claim. Newly expired sessions are claimed on the next sweep. Aborted unaccepted saves retire their upload and queue the known immutable object key; multipart cleanup uses the existing worker. Terminal session evidence remains immutable while cleanup lease fields can advance.

The broker must treat supplied session identities and operation idempotency keys as durable, enforce expiresAt, and make close idempotent with a tombstone that prevents a late open/save from reviving a closed session. Deployments must smoke-test their configured vendor broker, shared durable storage, scanner and scheduler. Deterministic HTTP broker fixtures verify the integration contract; native Google/Microsoft/OnlyOffice services have not been exercised. Full Files-module and repository regression remain pending.
