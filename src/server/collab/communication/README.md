# Chat metadata and membership

Communication owns persistent Chat metadata, membership rows and independent access sources. Task creation, subtasks and template instances provision one canonical Chat inside the business transaction. Every linked Task Chat read reevaluates Task permissions; broad Chat grants alone cannot bypass Task access. Manual membership changes are rejected for Task Chats. Task lifecycle freezes/restores or detaches the resource, preserving retained history.

Project Chat provisioning is canonical and lazy through the Project resource port. Membership synchronization changes only PROJECT sources; direct MANUAL grants survive Project removal. Active internal Workspace membership is always required. Archive freezes membership changes, unarchive restores them, and hard deletion detaches the archived resource while retaining source history.

The authenticated router exposes metadata and member reads for DIRECT, GROUP, PROJECT, DEPARTMENT, TASK and COLLAB Chats. `POST /chats` creates a Group (optional `type: GROUP`), with the creator as administrator; `POST /chats/direct` resolves one canonical normalized internal-user pair. Membership is mandatory even with a Workspace-wide Chat grant. Group changes require `chat.member_manage` plus administrator or Workspace-owner authority, preserve retry identity, and cannot remove the last active administrator. Direct pair membership is protected from independent changes.

Department changes provision/synchronize their canonical Chat through the owning Department service. Reads also evaluate the live Department, manager and members, so stale membership-source rows never preserve revoked access. Department membership is protected from manual Chat changes. Collabs supply restricted space/membership authority through `ensureCollabChat`; the invitation and broader Collabs endpoints remain separate work. Internal and external members require active live Collab authority. Archived Collabs retain read access and report read-only status.

External identities without ordinary Workspace membership can use only `GET /chats/:id` and `GET /chats/:id/members` for an explicitly authorized Collab Chat. This read path never constructs or grants a Workspace role; other Chat reads return `CHAT_NOT_FOUND`, and writes/ordinary Workspace APIs still require Workspace membership. PostgreSQL checks canonical Direct pairs, typed source links, protected source kinds and tenant references. Invitation orchestration and the remaining Communication areas (Feed, Channels, Collabs, Calls) remain unfinished.

## Messages

`GET/POST /chats/:id/messages`, `GET/PATCH/DELETE /messages/:id` and the reaction, pin, favorite, read, draft, search, version and create-task/create-event routes operate on durable Messages. Every operation re-evaluates live Chat authority; unreadable Messages return `MESSAGE_NOT_FOUND`. Each Message has a per-Chat `sequence`: clients that miss realtime hints reload with `afterSequence=<last seen>&sortOrder=asc`. `clientMessageId` is required; the same sender retrying the same content receives the original Message, while different content returns `MESSAGE_CLIENT_ID_CONFLICT`.

Senders edit (`chat.message_edit_own`) and delete (`chat.message_delete_own`) within `settings.chatMessageEditWindowSeconds` (default 86400). Moderators (`chat.moderate` plus Chat administrator, Project manager or Workspace owner) may delete later; moderator deletions are audited. Edits store immutable pre-edit versions; deletion leaves a tombstone. Chat read positions only advance; exact receipts are stored for Chats with at most 50 members and are visible with `chat.read_receipts`. Drafts are private and versioned per user. Task/Event creation from a Message uses the caller's own Task/Calendar authority and stores an immutable communication binding. Permissions added: `chat.update`, `chat.message_edit_own`, `chat.message_delete_own`, `chat.moderate`, `chat.read_receipts`.

## Channels

`/channels`, `/channel-posts` and `/channel-comments` implement subscription publishing spaces (distinct from Group Chats). PUBLIC Channels are discoverable and readable by active internal members with `channel.read`; PRIVATE Channels exist only for members. Membership is the live union of direct grants and Department/Project links (`POST /channels/:id/members` with `sourceType`/`sourceId`, `active: false` unlinks), so removing one source never revokes access another still grants. One owner holds a direct grant and transfers ownership via `PATCH /channels/:id/members/:userId { role: "OWNER" }`. Publishing requires `channel.publish` and the OWNER/ADMIN/PUBLISHER role; comments follow the Channel `commentPolicy`; moderators (`channel.moderate` + ADMIN) delete with audit evidence. Archived Channels are read-only; deletion is soft.

## Collabs

`/collabs` manages restricted spaces for internal members and invited external guests (`collab.create|read|update|member_manage|invite_external|archive`). Internal users are added directly; external people only through `POST /collabs/:id/invitations`, whose response returns the one-time token and `acceptPath`. Tokens are stored hashed, expire after `settings.collabInvitationExpiryDays` (default 7), rotate on resend and are single-use. `POST /public/collab-invitations/:token/accept` requires the invited person's own bearer token (no Workspace context). Guests read `GET /collabs/:id`, `/members`, `/resources` and the Collab Chat metadata by sending the host `x-workspace-id`; no Workspace role is ever constructed for them. Archive makes the Collab and its Chat read-only.

## Calls

`/calls` owns call lifecycle metadata and authorization; media rooms belong to the provider adapter (`CALL_PROVIDER_URL`, `CALL_PROVIDER_TOKEN`). `POST /calls` commits a RINGING reservation, creates the provider room idempotently and records provider failures as FAILED calls (`CALL_PROVIDER_ERROR`, 502). Join/start responses carry participant media tokens and are never cached. `POST /calls/:id/external-invitations` returns a one-time call-scoped guest link; `POST /public/calls/:token/join` returns media access only. Recordings are Files linked on end when Workspace policy and the call allow it; `GET /calls/:id/recording` issues the standard File delivery path.

## Feed

`/feed` and `/polls` implement recipient-based broadcasts (not Chat). Authors target WORKSPACE (`feed.post_workspace`), USER, DEPARTMENT or PROJECT recipients they may address; ordinary audiences are resolved live, while announcements snapshot their published audience for stable acknowledgement metrics (`GET /feed/posts/:id/read-stats`). Mentions only reach users who can see the post. Anonymous polls never expose voter identity. Soft-deleted posts leave the feed; moderators (`feed.moderate`) can permanently remove them with audit evidence.
