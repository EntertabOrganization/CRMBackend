# Booking pages

Protected page configuration is available through `/api/v1/booking-pages` and its ID, publication and rules routes. Pages start as `DRAFT`; direct status writes are rejected. Publishing requires a live internal host, an active writable target Calendar and configured availability rules. Removing a page soft-deletes and unpublishes it; its slug remains reserved.

Creation requires `calendarId`, `title`, a globally unique lowercase `slug` (3–80 letters/digits with single hyphens), and `durationMinutes` (1–1440). `ownerUserId` defaults to the caller and must be covered by the create/update action scope. The target Calendar must grant creation access. Optional settings are `bookingMode` (`AUTO_CONFIRM` or `REQUIRE_APPROVAL`), `timezonePolicy` (`HOST` or `INVITEE`), IANA `timezone`, `requirePhone`, notice/advance limits and before/after buffers. Name and email are mandatory. Timezone defaults to the target Calendar; maximum advance defaults to 90 days, and notice/buffers to zero.

GET/list/rules require scoped `booking.read`; create, change/delete/rules and publish/unpublish require scoped `booking_page.create`, `booking_page.update` and `booking_page.publish`, respectively. Foreign or out-of-scope IDs return the same `BOOKING_PAGE_NOT_FOUND` response. Internal page configuration never serves as anonymous authority.

PUT replaces configuration, resets omitted optional settings to defaults, and preserves the owner unless supplied. PATCH changes supplied fields. Updates/publication require the current page `version` or `If-Match`. Rules have a separate version: `GET /:id/rules` returns null before configuration; initial `PUT /:id/rules` requires version 0. Rules use the working schedule shape (`timezone`, ISO weekly windows, holidays and date overrides). A rule mutation also increments the page version so later finalization can detect configuration changes. PostgreSQL checks tenant links, shape/range constraints, immutable identities and exact version advancement. Mutations commit audit and outbox records with the configuration.

`GET /api/v1/public/booking/:slug` resolves only live published pages and exposes a whitelist of configured public fields. Internal page IDs, unavailable/draft/unpublished pages and inactive hosts all return the same 404. Host membership, target Calendar creation authority and writability are checked on each request. Page and slot reads share the repository's per-client rate limiter (60 requests/minute), returning `BOOKING_RATE_LIMITED` on exhaustion before database hydration.

`GET /api/v1/public/booking/:slug/slots` requires offset-aware `startAt` and `endAt` within 31 days. Optional `limit` is 1–100 (default 20); optional IANA `timezone` controls display for `INVITEE` policy. Slot instants remain offset-aware UTC, and duration is elapsed time across DST. The host and Workspace come from the publication; client-supplied identities are rejected. Slots intersect page rules, host/business schedules and authoritative private busy intervals, honor elapsed notice/advance bounds, and include before/after buffers within working windows. The display grid advances in 15-minute steps from the requested start. Dense recurrence coverage queues bounded durable rebuilds and returns HTTP 202 with empty slots until ready. Buffer-expanded reads are tiled within the 31-day rebuild budget.

Public creation, authorized approval/rejection/cancellation/rescheduling, and guest cancellation/rescheduling capabilities are now wired. Booking lifecycle notification delivery and configured attendee/resource reservations are integrated. Existing host holds constrain recurrence creation, rule changes, moved exceptions, future edits, root changes and attendee additions before mutation. Suggestions reserve nothing.

`GET /api/v1/bookings` and `GET /api/v1/bookings/:id` require `booking.read` and evaluate its scope against the reservation's original host in the active Workspace. Reads include all lifecycle states and remain available after page unpublication or deletion. A missing, foreign or out-of-scope ID returns `BOOKING_NOT_FOUND`. Responses expose reservation identity, page/Calendar/Event links, guest contact fields, times, status, version and timestamps; they never expose capability hashes/nonces, request fingerprints/keys, source revisions or reserved buffer boundaries. Reading creates no audit/outbox mutations.

Lists use the standard page/limit envelope (limit capped at 100), guest name/email search, status/page/host/Calendar/time filters and chronological sorting by `startAt` by default. Supported sort fields are `startAt`, `endAt`, `createdAt`, `updatedAt` and `guestName`. Filtering and sorting on internal security fields is rejected before returning data.

`PATCH /api/v1/bookings/:id` requires scoped `booking.update` against the original host, and the current Booking `version` or `If-Match`. It edits supplied `guestName`, `guestEmail` and `guestPhone` fields on active PENDING/CONFIRMED reservations. Name/email remain required; email is normalized and validated, and phone may be cleared unless required by page policy. Time, host, status and reservation selection changes use their existing action endpoints. Contact correction remains available after page unpublication/deletion. Identical values return the unchanged version without duplicate audit/outbox records.

Confirmed contact edits synchronize the bound Calendar guest through the internal Booking port, preserving reservation times and resources and writing Event history with the actual editor. Missing guests and conflicting guest emails fail closed. The transaction records `BOOKING.UPDATED` audit and `BOOKING_UPDATED` outbox evidence; the notification worker delivers the current contact change. Email reassignment rotates both guest capabilities and irreversibly disables capability recovery through the original public creation receipt. The changed guest receives its new link through the guest notification provider. Old creation-request retries continue returning reservation status/times but no capabilities, even after later reschedules. Current guest capabilities still rotate normally on rescheduling. PostgreSQL independently guards irreversible receipt revocation, token rotation and final-state Booking/Event guest consistency. Existing Booking writes use UPDATE, with a Workspace revision fence covering contact changes and current authorization.

The durable reservation foundation is now present: `calendar_bookings` stores request identity, versioned lifecycle state, capability hashes and host intervals including buffers. PostgreSQL excludes overlapping active host holds across pages, validates tenant parents, and defers confirmed Event links/alignment until transaction commit. Booking changes must persist before Event changes. One-off Event writes and attendee additions cannot cross a held host interval. Availability includes PENDING/CONFIRMED reservation intervals without exposing Booking identities or guest fields.

`calendar_availability_epochs` is a database-managed Workspace revision. Calendar, recurrence, schedule and authorization writes lock and advance it. Finalization commands read that revision and the page/rules versions, validate authoritative availability, and submit them while acquiring their reservation. The database rejects stale reads after waiting for concurrent source writes. This coarse Workspace fence can require retries after unrelated Calendar changes. Recurring Event writes acquire and validate the hydrated Workspace revision before persistence; Booking hold changes also advance it. A concurrently acquired PENDING hold therefore forces stale Event writers to retry. Configured attendees/resources participate in finalization using the reservation snapshot. Lifecycle notification delivery is documented in BOOKING_NOTIFICATIONS.md.

`POST /api/v1/public/booking/:slug/bookings` accepts `guestName`, `guestEmail`, optional/configured-required `guestPhone`, and offset-aware `startAt`. A high-entropy UUID `clientRequestId` or `Idempotency-Key` is required; both must agree when supplied. Guest identity and start time form a normalized request fingerprint. Retrying the same page/key/details returns the existing receipt without duplicate Events, audit or outbox writes; changed details return `BOOKING_IDEMPOTENCY_CONFLICT`. Server-side page duration, notice/advance limits, hours, buffers, host availability and publication authority are rechecked. Dense recurrence coverage returns HTTP 202 with `booking: null` and persists rebuild work, so the client retries without a partial reservation.

AUTO_CONFIRM creates a confirmed Booking, host attendee, external guest and busy Calendar Event in one transaction. REQUIRE_APPROVAL creates a pending host hold without an Event. `POST /bookings/:id/approve` and `/reject` require scoped `booking.approve`; `/cancel` requires `booking.cancel`; `/reschedule` requires `booking.update`. Administrative commands require the current Booking version or `If-Match`. Calendar writes use a dedicated internal Booking domain port, preserving the command's real actor in history; callers do not need unrelated Event permissions. Approval rechecks publication and availability while excluding its own hold, and rejects a changed requested duration. Rescheduling rechecks current hours/availability and reconciles the existing Event and attached resources. Ordinary Event endpoints cannot move, cancel, restore or make a confirmed Booking Event free independently of its Booking.

Public receipts contain only Booking ID, status, times, version and separate cancellation/reschedule capabilities. They disclose no Workspace, host, Calendar or Event IDs. Capability strings are purpose-scoped HMAC values derived from a random nonce and generation, with only hashes stored. Configure `BOOKING_TOKEN_SECRET` (at least 32 bytes); a configured `JWT_ACCESS_SECRET` can serve as the fallback outside tests. There is no production default key. Keep the signing key stable to reconstruct retry receipts; changing it does not revoke previously stored token hashes, but prevents recovery of their original receipts.

`POST /api/v1/public/bookings/:token/cancel` accepts an empty body. `/reschedule` requires offset-aware `startAt` and accepts an optional current `version`. A Booking ID, wrong-purpose token, expired token or revoked token returns the same `BOOKING_TOKEN_INVALID` response. Rescheduling rotates both capabilities; cancellation/rejection clears both hashes. Tokens expire seven days after the reservation end. Cancellation remains available after page unpublication, allowing the guest to release the hold. Raw capabilities, request fingerprints and nonces never enter audit, outbox or ordinary staff responses. Public creation and capability routes each limit clients to 10 writes per minute before hydration, returning `BOOKING_RATE_LIMITED` on exhaustion.

Booking pages accept scoped attendeeUserIds and resourceIds. Reservations snapshot this selection; later page edits do not change existing holds. Public availability intersects every selected subject and working schedule, including buffers, without disclosing their identities. Pending holds reserve every subject; confirmation creates internal attendees and resource reservations atomically. Approval and rescheduling recheck the original selection. Cancellation releases every hold. PostgreSQL guards preserve snapshots through upsert persistence and reject independent overlapping writes.
