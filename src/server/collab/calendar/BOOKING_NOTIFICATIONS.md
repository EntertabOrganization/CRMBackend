# Booking lifecycle notifications

Calendar's committed `BOOKING_CREATED`, `BOOKING_CONFIRMED`, `BOOKING_RESCHEDULED`, `BOOKING_CANCELLED`, `BOOKING_REJECTED` and `BOOKING_UPDATED` outbox events are durable notification intents. The worker ingests each event once, creates per-recipient deliveries transactionally, and uses PostgreSQL leases and idempotency keys across processes. Provider calls run outside business transactions. Completion writes queue evidence and a `BOOKING_NOTIFICATION_SENT`, `BOOKING_NOTIFICATION_SUPPRESSED` or `BOOKING_NOTIFICATION_FAILED` outbox event in one transaction.

Run the token-protected `POST /api/v1/internal/crm/jobs/booking-notifications` with optional `limit` (1–100). Schedule repeated runs until the backlog is empty. Delivery uses small waves, a 30-second provider timeout, a five-minute lease, and up to five attempts with exponential backoff. An abandoned final lease becomes an explicit exhausted failure. Older Booking versions are suppressed; live internal membership, attendee access and user preferences are rechecked. Notification queue rows are independently owned durable worker state and are excluded from business hydration/persistence.

The default shared NotificationPort delivers host/attendee inbox items. External guest email uses the optional `notifyGuests` provider method and fails explicitly when unconfigured; tests exercise a fake provider, not real email. Guest capability links are reconstructed only when dispatching the current Booking and never enter audit/outbox/queue payloads. Guest providers must honor the signal and deduplicate the supplied idempotency key.

Contact updates suppress prior-version notifications, and guest dispatch also checks that the queued email matches the current Booking. Following email reassignment, the new guest notification carries the newly rotated capability; the original public creation receipt can no longer recover it. Page-configured attendee/resource selection and recurring resource reservations are integrated.
